# 硬件、容量与运行环境约束

> 这份文档回答两个问题：**要什么样的机器才跑得动**，以及**录制的这几个小时里不能干什么**。
> 前者是配置门槛，后者不是洁癖——每一条都对应一次真实的废片，原因写在表里。

## 一、对 agent / 模型的依赖：运行时不需要，但有它明显更好

### ① 独立运行：不需要任何 agent 或模型

代码里没有任何网络调用，也没有任何模型调用，可自证：

```bash
grep -rn "requests\|urllib\|http.client\|openai\|anthropic\|api_key\|127.0.0.1" scripts/ || echo "无任何网络/模型调用"
```

判据全部是确定性的：

| 环节 | 判据 | 靠什么 |
|---|---|---|
| 页面就绪 | `readyState >= 2`、`duration` 有值 | 页面 DOM |
| 播放连续性 | `currentTime` 持续增长、无 seek、`rate == 1`、未静音 | 页面 DOM 轮询 |
| 会话安全 | 未锁屏、在控制台、目标窗口在前台 | `CoreGraphics` 会话信息 |
| 磁盘 | 余量高于阈值 | `statvfs` |
| 成品验收 | 能完整解码、能提取音轨、`volumedetect` 峰值高于静音阈值 | `ffmpeg` |

外部依赖只有系统命令：`screencapture`、`osascript`、`ffmpeg`、`pgrep`、`swift`。三条命令 + 一份队列就能跑完一整批，夜间无人值守由 `night_guard.py` 负责。**不给任何模型，它照样录完。**

### ② 接入 agent 之后：监督更早，纠错更快

工具本身只在「录一个文件」这个尺度上做判断。跨课、跨小时的问题，需要外部观察者。接一个能读状态与日志的 agent（本地模型或云端模型都行），它能盯这些：

| 它能盯的 | 没有它会怎样 |
|---|---|
| 播放是否真的在推进（`currentTime` 两次采样对比） | 进程都在跑，画面停在第 3 分钟，要等到验收才失败——白录两小时 |
| 连续失败是不是同一根因 | 每课各自重试，一天白跑；还把课静默塞进 blocklist |
| 状态与磁盘是否一致（标 `completed` 但文件不在） | 最后对账才发现，缺的课要再排一轮 |
| 开录那一刻的前置条件（前台、锁屏、磁盘、GPU 负载） | 点击失败、0 字节、锁屏中断，其实在开录瞬间就注定了 |
| 失败后的状态修复（重置 `pending`、清理残留窗口、过 preflight） | 得有人读代码才会做，往往一停半天 |

换句话说：**录制逻辑不需要 AI，但「什么时候该干预」这个判断，AI 比定时脚本敏感得多。**

接入不需要改代码——`batch-state.json`、每课的 `.recording.json` sidecar、守护日志都是明文，agent 读这些就能监督。缺的是机器可读的 `--status --json`（见 [roadmap](roadmap.md)）。

### ③ 依赖度分级

| 场景 | 需要 agent / 模型吗 | 说明 |
|---|---|---|
| 录一节课 | 不需要 | 三条命令 + 一份 `queue.json` |
| 录一整批无人值守 | 不需要 | `night_guard.py` 保活、卡死检测、失败隔离；人每天看一次 `--status` |
| 抓新内容 | 不需要模型，但**需要人** | 队列必须外部生成，工具不自己发现内容 |
| 出异常后恢复 | **有 agent 明显更好** | 判断「坏文件还是环境抖动」、重试还是隔离、状态手术 |
| 改代码/换平台 | **有 agent 明显更好** | 重写 DOM 选择器与点击路径 |

### ④ 反例：判据错了，agent 会把它执行到底

本地模型曾据「`screencapture` 中途没有 `.mov` 文件」判定采集卡死，进而判出「GPU 硬件故障、建议送修」。实际上 `.mov` 是**录完才落盘**的，这个判据本身就不成立。

结论不是「别用模型」，而是：**用可自证的物理指标给它当尺子**——抓帧能否出数据、`currentTime` 是否推进、`ffprobe` 能否解出音轨。监督类工作的价值取决于判据是否可靠，而不是模型有多强。

## 二、实测设备（作者机器，不是要求）

| 项 | 值 |
|---|---|
| 机型 | Mac Studio（Mac17,14） |
| 芯片 | Apple M5 Max，18 核 CPU（6 Super + 12 Performance），**40 核 GPU** |
| 统一内存 | 128 GB |
| 系统 | macOS 27.2.1（26B131） |
| 显示 | 主屏 5120×2880（UI 2560×1440 @60Hz）+ 外接 1440×3440 竖屏 @50Hz |
| Python | 3.9.6（`/usr/bin/python3`，系统自带） |
| ffmpeg | 9.0.1（必需） |
| 浏览器 | Chrome 158 |

实测产物规格（同一套代码，两种窗口尺寸）：

| 窗口 | 输出分辨率 | 帧率 | 时长 | 体积 | 折算 |
|---|---|---|---|---|---|
| 1330×750（小窗） | 1376×796 | 33.2 fps | 1:54:57 | 1.7 GB | ≈ **0.9 GB/小时** |
| 2560×1335（全屏） | 约 5120×2670 | 约 33 fps | 约 2 小时 | 5.5 GB | ≈ **2.7 GB/小时** |

整批实测：169 节课、159 个 `.mov`、合计 **409 GB**（含小窗与全屏两种配置，平均约 2.4 GB/课）。

## 三、最低配置（估算，非实测）

下面标「估算」的行没有在低配机器上验证过，别当成保证值。

| 项 | 最低（估算） | 推荐 | 依据 |
|---|---|---|---|
| 系统 | macOS 12+ | 与作者同代的 macOS | `screencapture -l/-A` 与 AppleScript 驱动都是系统能力 |
| 芯片 | Apple Silicon（M1 起） | M 系列 Pro / Max | **未在 Intel Mac 上验证**；编码走 VideoToolbox 硬编，不需要独显 |
| 内存 | 8 GB | 16–32 GB | 录制进程本身很轻（<500 MB），大头是 Chrome 播视频 + 系统 |
| GPU | 集显足够 | 别让 GPU 被占满 | 见第四节「GPU 争抢」：被占满时采集会写 0 字节 |
| 可用磁盘 | 100 GB（约 30 课） | 500 GB 以上 | 脚本自带 60 GB 停机下限 + 每课预留 30 GB 护栏 |
| 显示 | 单屏 ≥1280×800 | **只用主屏** | 外接竖屏上合成点击到不了网页（实测），小窗也要 ≥1280 宽才保证文字可读 |
| 权限 | 屏幕录制 + 辅助功能 | 同左 | 缺任一项：截图失败 / 原生点击失败 |
| 网络 | 稳定即可 | 有线或 5GHz | 流媒体加载慢会触发「就绪超时」，重试次数有限 |

容量估算公式（按小窗 0.9 GB/小时、全屏 2.7 GB/小时）：

```
总容量 ≈ 课程节数 × 平均时长(h) × 单小时码率
例：169 节 × 2 h × 1.2 GB/h ≈ 400 GB
```

**预留一倍**：失败重录、`.mov` 与 remux 后的 `.mp4` 同时存在、失败半截文件按规则保留——实际占用常是「成品体积」的 2 倍。

## 四、录制期间的行为约束

每条约束后面是**违反的后果**，不是建议。

| 别做 | 后果 | 为什么 |
|---|---|---|
| 听音乐 / 看别的视频 / 语音通话 | 声音混进成品，整节课要重录 | `-A` 抓的是**系统最终混音**，不是「只看这个窗口就只录这个窗口的声音」 |
| 玩游戏**并且开着声音** | 同上；实测成品音频均值抬升约 6 dB | 视频只抓自己的窗口，音频却是全系统的 |
| 把系统音量调小或静音 | 验收判「静音」→ `failed` | 验收看的是音轨峰值，不是画面 |
| 连蓝牙耳机 | 可能录出全静音轨 | 输出切到蓝牙后 `-A` 的抓取行为不可靠 |
| 锁屏 / 让它自己进屏保 | 当前课安全中止并判失败 | 锁屏画面不能当课程录，`session_guard` 会直接停 |
| 每节课开头的 1–2 分钟切到别的 App | 本次尝试失败（有重试，但会消耗次数） | 原生播放点击要求点击瞬间目标窗口在前台 |
| 录制期间启动新的浏览器实例 / 自动化工具 | 大概率当前课失败 | 新实例会抢走前台；有些工具还会自己开 Chrome |
| 动录制窗口的标签页（新开、关闭、拖出） | 本次尝试中止 | 「自有窗口标签数变化」触发安全守卫，防止录到错误内容 |
| 录制期间加载大模型 / 跑重 GPU 任务 | 采集写不出帧，成品 0 字节 | 合成器（WindowServer）与采集、Chrome 解码共用 GPU |
| 队列在跑的时候改 `queue.json` / `batch-state.json` | 状态错乱，可能重复录或漏录 | 队列是输入事实，状态是运行结果，工具按自己的原子写入约定维护 |
| 拔外置盘 / 切换输出设备 | 正在写的文件损坏 | 输出路径在录制期间必须稳定 |

想「一边录一边用电脑」的唯一安全做法：**只读的纯命令行操作**（`grep`、`sqlite3`、`curl` 这种不改变前台应用、不播放声音的）。

> 已经自动挡住的：时间窗、`STOP`、单实例锁、磁盘余量、锁屏、标签数变化、失败重试上限、连续失败进 blocklist。
> 半自动的：GPU 争抢。`night_guard.py` 每轮把 `WindowServer` 的 CPU 占用写进守护日志（`[诊断]` 行），但不据此阻断启动——它只是事后判据，别指望它替你拦住游戏。
>
> **没有**自动挡住的：音频被其他应用污染（只能靠事后 `volumedetect` 发现）、GPU 争抢、用户抢前台。这三项靠上面的行为约束。
